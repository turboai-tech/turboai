# FDE 需求自动化 —— 系统设计 v0.1

> 目标读者：技术负责人 / 首批工程团队
> 范围：把「企业 AI 战略升级」的需求，从对话输入自动转化为可交付、可追溯的方案
> 状态：**待确认**（见第 9 节）。本文是定义草案，不是已批准方案。

---

## 0. 为什么先写文档

原始需求是「FDE 面向企业 AI 战略升级的需求自动化 build」。这句话里三个词都需要先钉死才能动工：

- **FDE** 做的哪一段？（发现 / 拆解 / 估算 / 提案 / 实施 / 交接）
- **自动化**到什么程度？（辅助人 / 人审的草稿 / 全自动）
- **build** 出什么？（一份文档 / 一个方案包 / 可运行的系统）

这三个问题的不同答案，对应的工程量差 5 倍以上。直接写代码极可能做错方向，所以先出定义。

---

## 1. 产品定义

### 1.1 FDE 工作的分解

Forward Deployed Engineer 面向企业客户的完整链路：

```
① 发现        与客户对话，理解业务，找到 AI 可切入点
② 拆解        把「我们想上 AI」变成具体、可建的工作流
③ 估算        工作量、周期、依赖、风险
④ 提案        客户会签字确认的交付物
⑤ 实施        真正把系统建出来
⑥ 交接        培训、文档、运维移交
```

### 1.2 本项目的范围

**做 ①→④，不做 ⑤⑥。**

理由：⑤ 的自动化就是「自动写整个企业系统」，当前技术做不到，硬做出来的东西没人敢上生产。而 ①→④ 恰恰是 FDE 最耗时、最难规模化、也最标准化的部分——一个资深 FDE 花 2–4 周做的事，如果能压缩到 2 天且质量可控，这个价值足以独立成立。

### 1.3 一句话定义

> 把企业的模糊 AI 诉求，转化为一份**每条结论都能追溯到客户原话**的战略升级方案。

---

## 2. 三个决定成败的判断

### 2.1 交付物是「承诺」，不是「文档」

客户会拿这份方案去申请预算、定 KPI、跟供应商谈判。**方案错了比没有方案更糟**——没有方案客户只是原地不动，方案错了客户会照着错的方向投钱，几个月后发现走不通。那时损失的不只是这一单，是整条业务线的口碑。

这与 [ignition](https://github.com/xushaoxiao/Ignition) 里「账单错了比服务挂了更伤」是同一类判断：**产出物的价值 100% 建立在可信之上**。所以系统的核心不是「生成能力」，而是**可追溯性**。

### 2.2 幻觉是唯一会杀死产品的失败模式

LLM 生成战略方案时，最危险的不是写得不好，而是**写得很好但是编的**：

- 编造客户没说过的业务痛点
- 虚构客户不存在的系统和数据
- 给出看似精确实则凭空的 ROI 数字

这类内容极难被客户当场识破（听起来都对），却会在实施阶段全面崩塌。

→ **对策：溯源强制（Grounding Enforcement）。** 方案里每一条实质性结论，必须携带一个指向输入证据的引用 ID。生成阶段拿不到证据的结论，**不允许进入交付物**，只能进入「待确认清单」。

这条约束的地位等同于 ignition 的「只对确定性归因计费」——**宁可少写，不可编造**。

### 2.3 不要做全自动，要做「高质量草稿 + 人类签字」

全自动交付在这个场景不成立：责任无法转移。客户追责时，不能回答「是 AI 生成的」。

→ 系统的定位是**把 FDE 的产出效率提高一个量级，而不是取代 FDE**。每份方案必须有一个具名的人类 owner 签字放行，签字动作要落库、可审计。

## 3. 核心链路

```
① 需求录入                     ② 结构化抽取                ③ 缺口识别
┌──────────────┐              ┌──────────────┐          ┌──────────────┐
│ 访谈记录/问卷 │  ──────────► │ 业务现状      │ ───────► │ 信息缺口清单  │
│ 现有系统清单  │              │ 痛点          │          │ ↓            │
│ 上传的资料    │              │ 目标/约束     │          │ 回问客户      │
└──────────────┘              └──────────────┘          └──────┬───────┘
      │                              │                         │
      │  每条抽取结论都绑定           │                    补充后回到 ②
      │  evidence_id → 原文片段       │
      ▼                              ▼
                        ④ 方案生成（异步长任务）
                        ┌────────────────────────────┐
                        │ 场景矩阵：哪些业务环节可上 AI │
                        │ 优先级：价值 × 可行性         │
                        │ 分阶段路线图                 │
                        │ 所需能力/数据/组织准备         │
                        │ 风险与前置条件               │
                        └────────────┬───────────────┘
                                     │ 每条结论携带 evidence_id
                                     ▼
                        ⑤ 人工复核与签字
                        ┌────────────────────────────┐
                        │ FDE 逐条审阅 / 修改 / 驳回    │
                        │ 无溯源的结论必须显式处理       │
                        │ 签字 → 冻结版本 → 导出        │
                        └────────────────────────────┘
```

**关键设计**：③ 的「缺口识别」不是可选项。系统必须**主动承认自己不知道什么**——这既是防幻觉的机制，也是产品最像资深顾问的地方（新手才不敢问问题）。

## 4. 领域模型

### 4.1 复用现有 autoTask，不另起炉灶

现有 `server/routers/auto_tasks.ts` 已经具备本项目需要的全部基础设施：

| 已有能力 | 本项目如何用 |
|---|---|
| `task_code` 区分任务类型 | 新增 `fde_extract` / `fde_generate_plan` 等 code |
| `JOB_STATUS_*` 状态机 | 方案生成是分钟级长任务，天然需要 |
| `attempt` / `FAILED_RETRY` | LLM 调用不稳定，重试是刚需 |
| `payload` / `result` JSON | 输入输出结构差异大，JSON 合适 |
| `scheduled_at` / `expired_at` | 长任务的超时与调度 |

**判断：方案生成走 autoTask 提交到后端流水线，不在 Next.js 进程里同步跑。** 一次完整生成涉及多轮 LLM 调用，耗时以分钟计，同步请求必然超时。

### 4.2 新增实体

```
Engagement（一次客户服务）
 ├── owner_user_id        ← 必须有具名 FDE，责任不可转移
 ├── client_org           客户组织
 ├── status               drafting | reviewing | signed | archived
 │
 ├── SourceDocument[]     原始输入：访谈记录、问卷、上传资料
 │    └── chunks[]        切片，每片有稳定 ID —— 溯源的锚点
 │
 ├── Finding[]            结构化抽取结论
 │    ├── type            current_state | pain_point | goal | constraint
 │    ├── content
 │    ├── evidence_ids[]  ← 指向 chunk。**空数组不允许进交付物**
 │    └── confidence
 │
 ├── Gap[]                信息缺口
 │    ├── question        要回问客户的问题
 │    └── status          open | answered
 │
 ├── PlanVersion[]        方案版本
 │    ├── generated_by    task_id → autoTask
 │    ├── sections        JSON
 │    ├── grounding_rate  有溯源的结论占比 ← 质量核心指标
 │    └── status          draft | reviewed | signed
 │
 └── ReviewAction[]       复核动作
      ├── actor_user_id
      ├── action          accept | edit | reject
      └── target          finding_id / section_id
```

### 4.3 溯源的数据结构

这是整个系统的技术核心：

```ts
type Finding = {
  id: string;
  content: string;
  // 空数组 = 无溯源。这类 Finding 只能出现在「待确认清单」，
  // 不能出现在交付物正文 —— 由类型和落库校验双重保证。
  evidence_ids: ChunkId[];
};
```

**`grounding_rate`（有溯源结论占比）是这个产品唯一真正重要的质量指标。** 它应该展示给 FDE，也可以展示给客户——「这份方案 92% 的结论可追溯到您提供的材料」是极强的信任背书，也是竞品含糊带过的地方。

## 5. 与现有架构的接入点

```
app/dashboard/                  现有后台 → 扩展为 Engagement 工作台
  └── engagements/[id]/         新增：录入 / 复核 / 导出

server/routers/
  ├── _app.ts                   注册 fde router
  └── fde.ts                    新增：Engagement / Finding / Plan 的 CRUD

server/backend_proxy.ts         复用：LLM 与长任务都走外部后端
```

### 5.1 一个必须先解决的前置问题

**Prisma 目前完全未配置**——`prisma/schema.prisma` 里 datasource 和 generator 都是注释状态，没有任何 model。当前数据全部经 `BackendProxy` 转发到外部 `mac-ai` 后端。

所以第 4 节的实体要落在哪里，是个**架构决策，不是实现细节**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 启用 Prisma，本地建库 | 前端团队可独立迭代，溯源查询灵活 | 引入新的数据库运维；与现有后端的数据边界要划清 |
| B. 全部放外部后端 | 与现有架构一致，无新增运维 | 每个字段变更都要等后端排期，迭代速度受制于人 |
| C. 混合：溯源数据本地，任务执行走后端 | 迭代快 + 复用现有流水线 | 两处存储，需明确边界 |

**倾向 C**，但这取决于外部后端团队的配合意愿和排期——这不是我能替你判断的（见第 9 节）。

## 6. 不可违反的约束

参照 ignition 的做法，先立约束，再写代码。

| # | 约束 | 落地方式 |
|---|---|---|
| **C1** | 无溯源的结论不得进入交付物 | `evidence_ids` 非空是入库校验；渲染层按类型分区 |
| **C2** | 每份签字方案必须可完整复算 | 冻结版本时快照：输入 chunks、prompt 版本、模型 ID、生成参数 |
| **C3** | 交付物必须有具名人类 owner | `signed` 状态迁移强制要求 `actor_user_id` |
| **C4** | 版本只增不改 | 已签字的 PlanVersion 不可编辑，修改产生新版本 |

**C2 的具体含义**：三个月后客户质疑「这条结论怎么来的」，必须能回答。所以 prompt 也要版本化——prompt 变更等同于业务规则变更。

## 7. MVP 范围

### 明确不做

多租户隔离 · 客户自助门户 · 实时协作编辑 · 方案自动实施 · 多语言方案输出 · 计费

### 做（按依赖顺序）

1. **Engagement + SourceDocument + 切片**：能上传/粘贴材料并稳定切片。溯源的地基，必须先有。
2. **结构化抽取 + 溯源绑定**：走 autoTask 异步执行，产出带 `evidence_ids` 的 Finding。
3. **缺口识别**：产出要回问客户的问题清单。
4. **方案生成**：基于 Finding 生成分节方案，每节携带溯源。
5. **复核工作台**：逐条 accept/edit/reject，`grounding_rate` 可见。
6. **签字与导出**：冻结版本 + 导出 PDF/Docx。

### 验证指标

| 指标 | 目标 | 不达标的含义 |
|---|---|---|
| `grounding_rate` | > 85% | 溯源机制没兜住，幻觉风险高，产品不可用 |
| FDE 复核耗时 | < 4 小时/份 | 草稿质量不够，没比人工写快多少，价值不成立 |
| 复核驳回率 | < 20% | 生成质量不过关 |
| 客户签字通过率 | > 70% | 方案本身没解决客户问题，要回到定义 |

**第一个指标是生死线。** 如果 `grounding_rate` 上不去，整个产品定位需要重做，而不是继续加功能。

## 8. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 客户输入材料质量差（口头为主、无文档） | 无米之炊，溯源率必然低 | 提供结构化访谈问卷，把「收集」也变成产品的一部分 |
| 生成的方案千篇一律 | 客户觉得没价值，不如找人 | 场景矩阵要绑定行业知识库，而非纯 LLM 自由发挥 |
| 溯源被形式化 | 每条都引一段但引得不对，比没有更危险 | 复核工作台必须能一键跳转到原文；抽样人工校验引用准确率 |
| 企业数据敏感 | 客户不敢上传材料 | 数据隔离与留存策略要在售前就讲清楚，不能事后补 |

## 9. 待确认（阻塞性）

这些问题不定，无法进入详细设计：

1. **第一批客户是谁？** 是你们自己的销售/交付团队在用（内部工具），还是卖给外部咨询公司（SaaS）？这决定要不要从第一天做多租户，工程量差一倍。

2. **数据落在哪里？** 第 5.1 节的 A/B/C 三选一。取决于外部 `mac-ai` 后端团队的配合意愿和排期——如果每个字段变更都要等他们，方案 B 会拖垮迭代速度。

3. **LLM 从哪来？** 走现有 `mac-ai` 后端代理，还是前端直连模型厂商？涉及密钥管理、成本归属、以及企业客户对数据出境的要求。

4. **「AI 战略升级」的边界？** 是泛行业通用，还是聚焦你们已有积累的领域（现有 `auto_video_mix_clip_task` 显示你们在 AIGC 内容生成上有沉淀）？**聚焦垂直领域的方案质量会显著更高**，泛化则更容易做成千篇一律的模板。

## 附：与现有资产的关系

turboai 现有的 `autoTask` 流水线（异步任务 + 状态机 + 重试 + JSON payload）是这个产品最有价值的既有资产——它恰好是长耗时 AI 生成任务需要的基础设施。**本方案的核心工程判断就是复用它，而不是另起一套。**
